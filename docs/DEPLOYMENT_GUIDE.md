# Deployment Guide — Ship MVP 1 for Free (Phase 12)

This guide takes the finished Job Tracker (Phases 0–11) from local Docker to a
live, public deployment using **only free tiers**:

| Piece            | Free host                          | What it runs                       |
| ---------------- | ---------------------------------- | ---------------------------------- |
| PostgreSQL       | **Neon** (free tier)               | `users`, `jobs`, `job_notes`, admin |
| NestJS API       | **Render** (free web service)      | `backend/` via `backend/Dockerfile`|
| Next.js web app  | **Vercel** (Hobby)                 | `front/`                           |
| Browser extension| **Chrome Web Store** (see note)    | `extension/dist` zip               |

> **The one cost:** publishing to the Chrome Web Store requires a **one-time $5**
> developer registration (Google's fee, not recurring). Everything else is $0.
> If you want truly $0, skip the store and self-distribute the zipped extension
> (users load it unpacked, or you host the zip) — see [Step 5b](#step-5b--free-alternative-self-distribute).

**Architecture recap (why the env vars are shaped this way):**

```
Browser ──> Vercel (front)  ──/api/* rewrite──>  Render (backend)  ──SSL──>  Neon (Postgres)
Extension ─────────────────────────────────────>  Render (backend)  (direct, Bearer token)
```

The web app calls **its own origin** at `/api/*`; `front/next.config.mjs` rewrites
those to the backend. This keeps the httpOnly refresh cookies on the web origin
(required by the middleware). The **extension** calls the backend **directly** with
a Bearer token, so the backend CORS must allow the `chrome-extension://` origin
(it already does, via regex in `backend/src/main.ts`).

## Step 0 — Prerequisites (accounts, all free)

1. **GitHub** account (Render + Vercel deploy from your repo). Push this repo there.
2. **Neon** — https://neon.tech (free Postgres).
3. **Render** — https://render.com (free web service).
4. **Vercel** — https://vercel.com (Hobby tier).
5. **Cloudflare Turnstile** — https://dash.cloudflare.com → Turnstile (free CAPTCHA keys).
6. **Google Cloud Console** — only if you want live Google sign-in (free).
7. **Chrome Web Store developer** — https://chrome.google.com/webstore/devconsole ($5 one-time, only for Step 5a).

Before you start, decide your two public URLs (you'll paste them into several places):

- Web app: `https://<your-app>.vercel.app`
- Backend: `https://jobtracker-api.onrender.com` (Render assigns this)

## Step 1 — Provision free PostgreSQL (Neon)

1. Neon dashboard → **Create a project**. Pick the free plan and a region close to
   your Render region (e.g. `us-east` ↔ Render `oregon`/`ohio`).
2. Copy the **connection string**. It looks like:
   ```
   postgresql://USER:PASSWORD@ep-xxxx-xxxx.us-east-2.aws.neon.tech/neondb?sslmode=require
   ```
3. **Keep `?sslmode=require` in the string.** The backend uses `node-postgres` v8,
   which reads `sslmode` from the connection string and enables TLS automatically —
   no code change is needed. The `node:20-alpine` runtime ships CA certificates, so
   certificate verification (`verify-full`) works out of the box.
   - If a provider ever uses a self-signed cert and verification fails, change
     `sslmode=require` → `sslmode=no-verify` (still encrypted, skips CA check).

> **No migration step.** This project does not use Prisma. `DbService.onModuleInit()`
> runs `initSchema()` on every boot, creating all tables/enums/indexes idempotently
> (`CREATE TABLE IF NOT EXISTS`, guarded enum creation, backfills). So the first time
> the backend connects to your empty Neon database, it builds the schema for you.

## Step 2 — Deploy the backend to Render (free)

The repo already contains everything Render needs:

- `backend/Dockerfile` — multi-stage build (compiles with dev deps, runs slim prod image).
- `render.yaml` — a **Blueprint** describing the free web service and its env vars.

### 2a. Create the service via Blueprint (recommended)

1. Render dashboard → **New +** → **Blueprint** → connect your GitHub repo.
2. Render reads `render.yaml` and creates a **free** web service `jobtracker-api`
   using `backend/Dockerfile`.
3. Open the service → **Environment** and fill every var marked `sync: false`:

| Env var                    | Value                                                                 |
| -------------------------- | --------------------------------------------------------------------- |
| `DATABASE_URL`             | Neon connection string **with `?sslmode=require`** (Step 1)           |
| `CORS_ORIGINS`             | `https://<your-app>.vercel.app` (your Vercel domain, comma-separated) |
| `JWT_ACCESS_SECRET`        | auto-generated by Render (or paste a long random string)              |
| `JWT_REFRESH_SECRET`       | auto-generated by Render (different from access)                      |
| `JWT_ACCESS_EXPIRY`        | `15m`                                                                  |
| `JWT_REFRESH_EXPIRY`       | `7d`                                                                   |
| `GOOGLE_CLIENT_ID`         | from Step 4 (leave empty to disable Google sign-in)                   |
| `GOOGLE_CLIENT_SECRET`     | from Step 4                                                            |
| `GOOGLE_CALLBACK_URL`      | `https://<your-app>.vercel.app/api/auth/google/callback`              |
| `TURNSTILE_SECRET_KEY`     | your **secret** Turnstile key (Step 3)                                |
| `TURNSTILE_ALLOWED_HOSTNAMES` | `<your-app>.vercel.app` (optional hostname allow-list)             |

> `PORT` is injected by Render automatically; `main.ts` already listens on
> `0.0.0.0:${PORT}`. Don't set it yourself.

4. **Save changes** → Render builds the Docker image and deploys.

### 2b. Verify it booted

- Open `https://jobtracker-api.onrender.com/api` in a browser → you should see the
  health string (`Hello World!`). Render also uses `/api` as the health-check path.
- Check **Logs**: you should see `Backend running on http://localhost:<PORT>/api`
  and no schema errors. On first boot it created all tables in Neon.

### 2c. Create the first admin

There is **no public "register as admin"** (by design — see Phase 7). Seed one:

- **Option A (Render Shell):** Service → **Shell** tab, then run:
  ```sh
  node -r dotenv/config dist/scripts/seed-admin.js
  ```
  (The compiled seed script ships in the image and uses only prod deps.)
- **Option B (one-off env):** Temporarily set `ADMIN_EMAIL`, `ADMIN_PASSWORD`,
  `ADMIN_NAME` as env vars on the service, redeploy, run the seed command above,
  then **remove** `ADMIN_PASSWORD` and redeploy again.

The seed reads `ADMIN_EMAIL` / `ADMIN_PASSWORD` / `ADMIN_NAME` and creates an
`ADMIN`-role user. Additional admins use **invite tokens** from `/admin` (never a
public form).

> **Free-tier caveat:** Render free web services **spin down after ~15 min idle**.
> The next request cold-starts in ~30–60 s. Fine for demos/portfolios; if you need
> always-on, upgrade Render or use a paid tier later.

## Step 3 — Real Cloudflare Turnstile keys (production CAPTCHA)

Local dev uses Cloudflare's public **test** keys (always pass). For production you
need **real** keys so the CAPTCHA actually protects login/register:

1. Cloudflare dashboard → **Turnstile** → **Add site**.
2. Widget mode: **Managed** (or Invisible). Hostnames: add `your-app.vercel.app`
   (and `localhost` for testing).
3. You get a **Site Key** (public) and a **Secret Key** (private).
4. Put them:
   - Backend env: `TURNSTILE_SECRET_KEY=<secret key>` (Step 2a table).
   - Vercel env: `NEXT_PUBLIC_TURNSTILE_SITE_KEY=<site key>` (Step 4).

The backend verifies the token server-side and **fails closed** — if Turnstile is
unreachable or the secret is unset, login/register are rejected (never let through).
The secret is server-side only and is never logged.

> CAPTCHA is intentionally **not** applied to Google sign-in or the extension
> (per the build rules) — only to `/auth/login`, `/auth/register`, `/admin/auth/login`.

## Step 4 — Deploy the web app to Vercel (free)

1. Vercel → **Add New… → Project** → import your GitHub repo.
2. **Root Directory:** set to `front` (Vercel must build the Next.js app, not the monorepo root).
3. Framework: **Next.js** (auto-detected). Build command `next build`, output default.
4. Add **Environment Variables** (Production + Preview):

| Env var                         | Value                                                              |
| ------------------------------- | ------------------------------------------------------------------ |
| `API_PROXY_TARGET`              | `https://jobtracker-api.onrender.com` (backend URL, **no `/api`**, no trailing slash) |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY`| your public Turnstile **site key** (Step 3)                        |

5. **Deploy.** Vercel builds `front/` (verified: `next build` passes, all routes
   including `/privacy` compile) and gives you `https://<your-app>.vercel.app`.

### 4a. Update the backend CORS now that you know the Vercel URL

Go back to Render → backend → **Environment** → set
`CORS_ORIGINS=https://<your-app>.vercel.app` and redeploy. (The `chrome-extension://`
origin is already allowed by regex in `main.ts`, so the extension works without extra CORS config.)

### 4b. Google sign-in (optional, free)

1. Google Cloud Console → **APIs & Services → OAuth consent screen**: configure it
   (External), add your email as a test user while unpublished.
2. **Credentials → Create credentials → OAuth client ID → Web application**:
   - **Authorized JavaScript origins:** `https://<your-app>.vercel.app`
   - **Authorized redirect URIs:** `https://<your-app>.vercel.app/api/auth/google/callback`
     (this routes through the Vercel `/api` rewrite to the backend — same pattern as local).
3. Copy the **Client ID** and **Client secret** into the backend env
   (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`) and set
   `GOOGLE_CALLBACK_URL=https://<your-app>.vercel.app/api/auth/google/callback`. Redeploy.

If these are empty, the backend reports Google sign-in as "not configured" and the
buttons are hidden — email/password still works fully.

## Step 5 — Build & publish the browser extension

### 5a. Chrome Web Store ($5 one-time)

1. **Point the extension at production.** In `extension/`, create `.env.production`:
   ```
   VITE_API_BASE=https://jobtracker-api.onrender.com/api
   VITE_WEB_ORIGIN=https://<your-app>.vercel.app
   ```
   (`config.ts` reads these at build time; localhost defaults remain for dev/tests.)

2. **Declare production hosts in `manifest.json`** (it's static JSON and cannot read
   env vars). Add your real origins so the extension may call the API and run the
   login-bridge content script:
   ```jsonc
   "host_permissions": [
     "https://jobtracker-api.onrender.com/*",
     "https://<your-app>.vercel.app/*",
     "https://*.linkedin.com/*",
     "https://*.indeed.com/*"
   ],
   "content_scripts": [{
     "matches": [
       "https://*.linkedin.com/*",
       "https://*.indeed.com/*",
       "https://<your-app>.vercel.app/*"
     ],
     "js": ["src/content.ts"],
     "run_at": "document_idle"
   }]
   ```

3. **Build & zip:**
   ```sh
   cd extension
   npm ci
   npm run build          # outputs extension/dist
   # zip the CONTENTS of dist/ (not the folder itself)
   ```
   Zip `dist/*` into `jobtracker-extension.zip`.

4. **Chrome Web Store Developer Dashboard** → **New Item** → upload the zip. Fill in:
   - **Single purpose:** "Save job postings to the user's Job Tracker account and
     track application status."
   - **Permission justifications:**
     - `activeTab` + `scripting` — read the job posting on the page the user invokes
       the extension on, to prefill title/company/location.
     - `storage` — keep the session token so "Save Job" works without re-login.
     - host `*.linkedin.com` / `*.indeed.com` — parse those boards' job pages.
     - host `jobtracker-api.onrender.com` — call the user's own backend.
     - host `<your-app>.vercel.app` — the extension-login bridge that hands the
       session to the extension.
   - **Privacy policy URL:** `https://<your-app>.vercel.app/privacy` (the page added
     in this phase — **required** because the extension reads page content).
   - **Remote code:** declare none (all logic is in the bundle).
   - Screenshots of the popup + dashboard, a 128×128 icon, category Productivity.
5. Submit for review (typically a few days). Use the **unlisted/testing** visibility
   first to smoke-test before going public.

### 5b. — Free alternative: self-distribute

Skip the $5 store fee: build `extension/dist` (with the production `.env.production`
and manifest hosts as above), zip it, and either:
- Host the zip (e.g. a GitHub Release) and have users **Load unpacked** / drag it
  into `chrome://extensions` with Developer mode on, or
- Keep it **unlisted** in the store if you later pay the fee.

The extension works identically; only the distribution channel differs.

## Step 6 — Smoke-test the full production pipeline

Run the MVP 1 "Definition of Done" loop against the **live** URLs:

1. Open `https://<your-app>.vercel.app` → **Register** a fresh account (CAPTCHA widget
   should appear and pass). You land on an empty dashboard.
2. Install the published/unlisted extension; click it → it opens
   `https://<your-app>.vercel.app/extension-login` → connect the session (popup shows
   your name).
3. Go to a real **LinkedIn** job → click the extension → confirm title/company/location
   prefill → **Save Job**.
4. Back on the live dashboard → the job appears in **SAVED** within seconds.
5. **Mark as Applied** (manual) → card moves to **APPLIED**; drag it through
   SCREENING → INTERVIEW → OFFER; add/edit/delete a **note**; search & filter; delete.
6. Refresh — everything persists. Log out, log back in.
7. **Admin:** log in at `/admin` with the seeded admin → see all users/jobs → suspend
   a test user → confirm that user is blocked.
8. **Isolation check:** as user B, try to open/edit user A's job → must 404 (no leak).

For the full scenario matrix (auto-detect apply, duplicate-save prevention, error
states, etc.) see **`docs/TESTING_GUIDE.md`**.

## Step 7 — Backups & monitoring (free)

- **Backups:** Neon free tier keeps a restore window; you can also branch/snapshot.
  For an extra safety net, run a scheduled `pg_dump`:
  ```sh
  pg_dump "$DATABASE_URL" -Fc -f backup.dump
  ```
  (e.g. a free GitHub Actions cron, or Neon's PITR).
- **Logs / uptime:** Render → **Logs** + **Metrics**; Vercel → **Logs** + **Analytics**.
- **Error tracking (optional, free):** Sentry free tier for both backend and front.
- **Cold starts:** if Render sleeps, the first request is slow — expected on free.

```
GOOGLE_CLIENT_ID=<optional>           GOOGLE_CLIENT_SECRET=<optional>
GOOGLE_CALLBACK_URL=https://<your-app>.vercel.app/api/auth/google/callback
# seeding (temporary, remove after): ADMIN_EMAIL / ADMIN_PASSWORD / ADMIN_NAME
```

### Front (Vercel)
```
API_PROXY_TARGET=https://jobtracker-api.onrender.com
NEXT_PUBLIC_TURNSTILE_SITE_KEY=<cloudflare site key>
```

### Extension (build-time, `extension/.env.production`)
```
VITE_API_BASE=https://jobtracker-api.onrender.com/api
VITE_WEB_ORIGIN=https://<your-app>.vercel.app
```

> **Never commit real secrets.** The repo only contains `.env.example` templates.
> JWT secrets, Turnstile secret, Google secret and the DB password live only in the
> host dashboards (Render/Vercel/Neon), which encrypt them at rest.

## Troubleshooting

| Symptom | Likely cause / fix |
| --- | --- |
| Backend logs `no pg_hba.conf entry ... SSL off` | `DATABASE_URL` is missing `?sslmode=require`. Add it (Step 1). |
| Backend logs a cert/`self signed` SSL error | Provider uses a private CA — switch to `?sslmode=no-verify`. |
| Tables missing on first boot | Backend never connected — check `DATABASE_URL` and Render logs; schema auto-creates on a successful connect. |
| Web app: API calls 404 / CORS | `API_PROXY_TARGET` wrong (must be the backend URL **without** `/api`), or `CORS_ORIGINS` on the backend doesn't include the Vercel domain. |
| Login/register always fails CAPTCHA | Real Turnstile keys not set, or site/secret mismatch, or hostname not allowed. Verification fails closed by design. |
| Google button missing / errors | `GOOGLE_*` env empty (disabled) or redirect URI doesn't **exactly** match Google Cloud Console. |
| Extension "Cannot reach the Job Tracker API" | Built without `.env.production` (still pointing at localhost), or manifest `host_permissions` missing the backend origin, or backend CORS. |
| Extension login bridge does nothing | Manifest `content_scripts.matches` missing `https://<your-app>.vercel.app/*`. |
| First request after idle is slow (~45 s) | Render free tier cold start — expected. |

## Definition of Done (Phase 12)

- [ ] Neon Postgres provisioned; backend connected and schema auto-created.
- [ ] Backend live on Render; `/api` health returns 200; admin seeded.
- [ ] Real Turnstile keys active; login/register pass a live CAPTCHA.
- [ ] Web app live on Vercel; register → dashboard → Kanban works end-to-end.
- [ ] (Optional) Google sign-in works with the production redirect URI.
- [ ] Extension built for production, hosts declared, zip uploaded to the store
      (or self-distributed) with the `/privacy` policy URL.
- [ ] Full smoke test (Step 6) passes against the live URLs.
- [ ] Backups + log/uptime monitoring enabled.

When all of the above is true, a friend can install the extension, create an
account on the live site, save a job from LinkedIn, and watch it move through the
Kanban board — **MVP 1 is shipped.**
